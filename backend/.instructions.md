# Backend Instructions — Django + DRF

## Stack

Django 5.0+ · Django REST Framework · PostgreSQL 16 + pgvector · Redis · Celery

---

## Project Layout

```
backend/
├── config/settings/{base,development,production}.py
├── apps/{users,jurisdictions,questions,quiz,progress,knowledge}/
├── core/{exceptions,pagination,permissions}.py
└── manage.py
```

---

## App Structure

Each app: `models.py` → `repositories.py` → `services.py` → `serializers.py` → `views.py` → `urls.py`

Optional: `signals.py`, `tasks.py`, `tests/` with factories.

---

## Layered Architecture

| Layer | Responsibility | Can Call |
|-------|----------------|----------|
| Views | HTTP, auth, serialization | Services, Serializers |
| Services | Business logic | Repositories, other Services |
| Repositories | Data access (queries) | Models, QuerySets |
| Models | Schema definition | Nothing |

**Rule:** Views never call Repositories directly. Services contain all business logic.

---

## Coding Standards

- Type annotations on all functions (including return types)
- Docstrings (PEP 257) on all classes and public methods
- Use Ruff for linting/formatting
- Prefer class-based views for complex logic, function-based for simple
- Use Django ORM; avoid raw SQL unless justified
- Use `uv` for dependency management

---

## Patterns

### Repositories
- Static methods for queries (`get_by_id`, `get_by_jurisdiction`, `create`, `bulk_create`)
- Return QuerySets or model instances
- Filter validated records by default

### Services
- Instantiate repositories in `__init__`
- Encapsulate business rules (e.g., adaptive question selection)
- Services can call other services

### ViewSets
- Keep thin — delegate to services
- Use `@action` decorator for custom endpoints
- Validate input via serializers before calling services

### Models
- Use `TextChoices` for enums
- Add indexes for filtered fields
- Use `PROTECT` for foreign keys that shouldn't cascade
- No business logic in models

---

## API Conventions

- Version prefix: `/api/v1/`
- Standard response: `{ success, data, meta }` or `{ success, error: { code, message, details } }`
- Use custom exception handler in `core/exceptions.py`

---

## Testing

- Use pytest + pytest-django (not unittest)
- Tests in `apps/*/tests/`
- Use factory_boy for test data
- Mark DB tests with `@pytest.mark.django_db`
- Type annotations and docstrings required in tests

---

## Celery Tasks

- Use `@shared_task(bind=True, max_retries=3)`
- Wrap in try/except with `self.retry(exc=exc)`

---

## Do Not

- Put business logic in views or models
- Query models directly in views
- Add apps/packages without updating ARCHITECTURE.md
- Modify settings without discussion
- Use raw SQL without justification
- Skip serializer validation
- Return non-standard response formats
- Make index's name no longer than 30 characters
